### 真实启动器联调

启动器以`-Drdi.sessionResume=true`运行，经真实master创建和启动Docker房间，用原版整合包进入：

```text
游戏 → 启动器进程内的DLL → 节点A/B（故障中继）→ proxy-rs → 真实master路由 → 房间容器
```

启动器进程里加载了含`rdi_lp_start`的DLL。启动器由`compose-hot-reload`的MCP接口操作，创建房间、进入房间和设置页切换都走真实界面。

| 项目 | 次数/版本 | 失败 | 1.21.1 P95 | 1.21.1 最大 | 1.20.1 P95 | 1.20.1 最大 |
|---|---|---|---|---|---|---|
| 节点进程退出 | 各12 | 0 | 4ms | 4ms | 3ms | 3ms |
| 节点完全静默 | 各12 | 0 | 3.02秒 | 3.02秒 | 3.00秒 | 3.00秒 |

两个版本都没有被踢，24次都在同一条连接上。负载流量都不大：跑图1.21.1约27KiB/s，1.20.1约85KiB/s。1.20.1这一轮启动器已升到Ktor 3.6.1。

| 其他项目 | 结果 |
|---|---|
| 设置页手动切换（1.21.1） | 切换1ms，没有断线；提示“已切换到<节点名>，不用退出地图”；当前节点显示随实际节点变化 |
| 启动器正常关闭（无游戏运行） | 0.5秒内退出，无残留进程，端口释放，DLL未被占用 |
| 游戏运行时强杀启动器 | 立刻退出，无残留进程，端口释放，DLL未被占用；游戏0.7秒内显示断线；锚点20秒后回收，服务端显示玩家离开 |

强杀后游戏进程仍在，停在断线界面，由玩家自己关闭。

master升到Ktor 3.6.1并重启后，又用真实房间复核：1.21.1和1.20.1房间都不带JWT连上了master；1.21.1经`proxy-rs`和master路由进入房间，断节点6次（退出、静默各3次）全部恢复，没有被踢。

有一次游戏启动时报`Failed to find a primary monitor`后退出，重启游戏后恢复。原因很可能是当时系统里没有可用的显示器，没有单独证实，所以测试期间要保持系统里有显示器。

开发环境下节点是本机地址，不在候选列表内，所以当前节点显示为“默认节点”。真实节点名称的显示要到第3阶段才能看到。

### DLL接真实游戏

开发客户端和服务端都是普通方式启动，只是不再直连：

```text
runClient → 本地端口（JVM经JNA加载的DLL）→ 节点A/B（故障中继）→ proxy-rs → runServer
```

DLL由`client/local-proxy-rs/jna-smoke/JnaProxyHost.java`加载，每500ms读一次事件，和启动器相同。启动器本身的`LocalMcProxyService`和设置页没有参与这次测试。

| 项目 | 次数/版本 | 失败 | 1.21.1 P95 | 1.21.1 最大 | 1.20.1 P95 | 1.20.1 最大 |
|---|---|---|---|---|---|---|
| 节点进程退出 | 各12 | 0 | 5ms | 5ms | 24ms | 24ms |
| 节点完全静默 | 各12 | 0 | 3.01秒 | 3.01秒 | 3.02秒 | 3.02秒 |
| 手动切换 | 各6 | 0 | 19ms | 19ms | 1ms | 1ms |

两个版本都没有被踢。每个版本的30次都由同一条连接完成，中途没有重新进入。

| 负载 | 1.21.1 | 1.20.1 |
|---|---|---|
| 站立 | 1.8KiB/s | 87KiB/s |
| 跑图 | 127KiB/s，共11MiB | 963KiB/s，共83MiB |
| `/recipe` | 1.7KiB/s | 130KiB/s |

- 1.21.1这轮流量偏低，不算大流量压力；1.20.1跑图的流量是真实的高负载。
- 1.21.1客户端启动时的第一次快速加入失败：`localhost`解析成了`::1`，而代理只监听`127.0.0.1`。走`127.0.0.1`的进房按钮能正常进入。启动器传给游戏的本来就是`127.0.0.1`，所以只影响这种开发环境接法。
- 1.20.1测试中另有18条立刻结束的短连接，与第1阶段记录的现象相同，不影响玩家连接。
- `local_proxy_stats`里约300MB的峰值包含JVM和Java源码编译，不代表DLL的内存占用。

### 手动游玩（1.21.1）

用户在客户端里实际游玩，脚本每30秒断一次当前节点，共13次（节点退出7次，静默6次），全部恢复，没有掉线。用户的评价：延迟可以接受。

挖方块时偶尔回弹，用户认为可以接受。这和普通卡顿的表现一致：服务端按开始和结束挖掘之间的tick数计算进度（`ServerPlayerGameMode`），静默恢复后两个包几乎同时到达，进度不足时会先把方块补回来，再按延迟破坏继续计算。这个解释来自源码，没有逐次对应验证。

陪玩模式用`resume_game_e2e.py --hold-fault-every 30`，在工作目录创建`resume_hold.stop`即可结束。

### macOS 15（GitHub Actions）

- 恢复模式负载：20个会话，480次切换，P50 3.00秒，P95 3.01秒，最大3.01秒，全部成功。
- 这台机器上无法测量内存（脚本只支持`/proc`），所以内存标准在macOS上没有结论。
- `macos-15`在公开仓库不计费（计费接口返回0）。
- 图形：`screencapture`能截到桌面，但`system_profiler`没有返回显卡信息。启动器界面截图是否可行，要等真正打开窗口才知道。

第一次运行时，`smoke_load.py`的后端不可用场景失败。这个场景用绑定但未监听的端口，脚本只等4秒，而代理的连接时限是5秒。放宽到7秒后通过，所以很可能是macOS上这种端口不立刻拒绝连接，但没有单独测量。

## 第1阶段结论（2026-11-02）

第1阶段的通过标准全部达到。本机验证覆盖了真实Minecraft客户端和服务端，但线路是本机回环，不代表公网表现。

## 通过标准

| 项目 | 标准 | 1.21.1 NeoForge | 1.20.1 Forge |
|---|---|---|---|
| 被踢次数 | 0 | 0（75次） | 0（75次） |
| 节点静默恢复 | P95≤8秒，最大<15秒 | P95 3.03秒，最大3.03秒 | P95 3.03秒，最大3.04秒 |
| 节点退出恢复 | P95≤3秒 | P95 26ms，最大32ms | P95 16ms，最大16ms |
| 手动切换 | 无明显卡顿，不断线 | P95 22ms | P95 19ms |

每个版本的75次由节点退出30次、节点静默30次、手动切换15次组成，平均分布在站立、跑图和大数据包三种负载下。整段测试玩家始终是同一条连接：1.21.1为22:45:59至22:52:42，1.20.1为23:17:27至23:27:57，中途没有离开或重新进入。

每次故障后都要求服务端回应一条命令，才算恢复成功。

## 第一次1.20.1完整测试的2次失败

第一次完整测试有2次被判定失败，修正测试脚本后重跑，75次全部通过。上表是重跑的结果。

- 第1次：脚本把另一个短连接的结束算成了玩家会话结束。事件记录显示玩家会话没有结束。
- 第2次：跑图时命令回复没有在2秒等待窗口内出现。当时服务端日志有2.2秒的卡顿，时间上吻合，但没有逐条对应证实。脚本改为等待5秒并最多重试4次后，75次都在第一次等待内得到回复。

## 短连接

1.20.1测试时，每分钟出现3条立刻结束的连接，1.21.1测试时没有。代码上很可能是本地master探测房间端口（`HostPresenceService`的`McServerPinger`），没有完全证实。它们不影响玩家连接。

## 复现

```sh
# 三个crate各自运行
cargo test
cargo test --release -- --ignored   # common/session-resume-rs：64MiB随机故障

# server/proxy-rs，加上恢复负载
python3 scripts/smoke_load.py --binary target/release/rdi-proxy-rs --connections 20 \
  --seconds 12 --resume-seconds 120 --favicon ../proxy/favicon.png \
  --local-proxy ../../client/local-proxy-rs/target/release/rdi-local-proxy-cli \
  --fault-relay ../../common/session-resume-rs/target/release/examples/fault_relay
```

真实游戏测试用`server/proxy-rs/scripts/resume_game_e2e.py`。先启动开发服务端，再启动脚本和客户端，脚本会点击游戏内的进入按钮。1.21.1要先把开发服务端临时改到其他端口，让出6370给本地代理；1.20.1的加入按钮连接51468，不用改服务端。
