# DM房间

Minecraft1.21.1 NeoForge客户端Mod负责创建和托管DM房间。`dm-master`保存永久房间与世界初始化资料，[dm-gateway](../../../server/dm-gateway/README.md)负责反向TCP转发。

## 配置

启动Minecraft时设置master的HTTP地址：

```text
-Drdi.dm.server=http://dm.example.com:8080
```

属性缺失、为空或格式无效时，不注册`/dm`命令，也不显示DM加入入口。客户端通过master的`GET /info`取得gateway的公网主机和隧道端口。

## 创建和托管

进入自己的单人世界后执行：

```text
/dm create 我的房间
```

创建进度界面会使用原版机制暂停尚未对外开放的单人世界。客户端在服务器线程保存世界后，将世界目录中除`.mca`、`.mcc`、`session.lock`、`rdi/host.json`及旧的`data/rdi_firm_sections.dat`、`data/rdi_firm_sections.dat_old`以外的文件打包。导出副本的`level.dat`和`level.dat_old`会移除`Data.Player`，原存档不会被修改。已经通过局域网开放的世界不会进入原版暂停状态，因此暂不能用此命令创建房间。

上传成功后，master生成永久UUIDv7房间ID。客户端将ID写入当前世界的`rdi/host.json`，在同一个世界中恢复游玩并建立隧道。以后进入这个世界会自动托管，退出世界会停止托管；无需`/dm host`或`/dm stop`命令。

```text
/dm status
```

用于查看当前房间ID和连接状态。网关或网络暂时中断时会后台重试；房间不存在、正在被另一个房主托管或没有可用游戏端口时停止重试并显示原因。

## 加入房间

配置有效时，多人游戏界面显示“加入DM房间”。输入房间ID后，客户端会：

1. 从master查询房间。
2. 下载或复用世界初始化资料。
3. 将资料保存在`<游戏目录>/rdi/dm/<hostId>/world/`，但不启动本地IGS，也不加入普通单人世界列表。
4. 再次查询当前游戏端口，然后通过gateway连接房主。

房主离线时仍可准备初始化资料，之后使用“加入/重连”再次查询。玩家也可手动重新下载；被替换的旧副本会移动到`<游戏目录>/DEL/rdi/dm/`。

## 同步区域标记（FirmSection）

1.21.1客户端的内置服务端只在DM房间中提供同步区域的设置、取消和自动设置。普通单人世界无法修改标记。标记包含维度、section坐标和归属玩家UUID，不包含方块、容器物品或其他世界内容。

`dm-master`按房间将列表和`revision`保存在`data/hosts/<hostId>/firm-sections.json`。房主只保留内存副本，加载成功后才能修改；设置或取消必须等master确认保存后才更新显示和通知玩家。访客继续接收房主发送的坐标显示包，无需直接访问master。

每次修改携带当前房主会话及`expectedRevision`。版本冲突后重新加载列表，不用新版本自动重放旧操作；请求超时后先核对服务器状态，结果未明确时暂停后续修改。网络断开时保留已确认的标记显示，恢复后重新加载。退出世界不会上传本地标记文件，也不会保留离线操作队列。

自动设置仍在放置带BlockEntity的方块时触发，开关只在当前世界会话内生效，重新进入后默认关闭。旧本地标记文件保留，不读取、不覆盖、不自动导入；新DM列表从空开始。

## 当前范围

本阶段保存不可变的世界初始化资料和可更新的同步区域标记。原版暂停会停止正常世界tick，但不会等待Mod自行执行的后台文件写入完成；初始化资料不是严格的文件系统同一时刻快照。尚未实现区域实际内容同步、备用IGS、自动接管、房主迁移、Mod兼容性校验或账户认证。会话检查用于拒绝失效房主连接的标记请求，不代替账户认证。初始化副本不能视为可接管的完整世界。

隧道协议只解析DMG1头和控制消息；Minecraft握手、压缩及加密后的数据均原样转发。真实双机联机和游戏内创建/重新打开流程仍需单独验证。

## 本地FirmChunk快照测量

作为DM房主进入本机世界，并确认同步区域资料已经加载后，可执行：

```text
/dm snapshot-test
```

命令只在当前客户端本地测量真实FirmChunk保存资料，不调用上传接口，也不连接网络。它会在单人世界服务器线程中执行一次完整保存、POI写入等待和选中区块列复制，然后在后台生成ZIP。结果保存在`<游戏目录>/rdi-snapshot-tests/run-*/`，包括`staging/`、`snapshot.zip`（成功时）和`metrics.json`。目录最多保留64次运行；单次最多256列，暂存NBT最多256MiB，失败目录也保留，旧结果不会自动删除。

每列按维度和`(chunkX,chunkZ)`去重，保存terrain、entities和POI记录；缺少entities或POI会在`metadata.json`中明确记录为本次快照的空/缺失记录。terrain会移除可重算的heightmap和计算光照数组，保留Mod附加数据。玩家资料及世界全局资料不在范围内，结果不能视为可恢复存档。

`metrics.json`和日志记录队列等待、服务器线程暂停、save/flush、复制、压缩、ZIP字节数及实际tick间隔。保存和复制期间服务器线程被同步占用，大型世界可能造成玩家掉线；这里没有计时器、恢复或迁移验证。建议在真实Mod整合包存档副本上分别测试空闲、机器运行和玩家移动/区块进出场景，每种场景先收集20至30次，并保留首次冷运行、失败和慢运行结果。

`pauseMs`包含保存、写入等待与独立复制；`packMs`在服务器线程释放后计时。`firstPostCaptureTickGapMs`比较捕获前后相邻的服务器tick；暂停菜单或世界退出导致无法观测时记录为`null`。`queueMs`单独记录任务排队，不计入暂停。保存期间观察到ERROR/FATAL或与保存相关的WARN会使该次测量失败；无关Mod日志也可能导致保守拒绝。Mod自行执行的后台写入不由此流程协调，ZIP通过检查不能证明恢复正确。
